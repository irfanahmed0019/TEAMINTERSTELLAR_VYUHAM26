# Struggle loop implementation and evidence limits

## Diagnosis is separate from error grouping

Two repeated graded failures create an observed pattern. Compile, runtime, output-format and test-name grouping are not proof of carelessness, a thinking style or a conceptual root cause.

The recovery page asks one versioned prediction probe for each supported study concept, in C or Python. The first prediction is saved before the model is shown. The learner then confirms or rejects whether the proposed rule caused the original mistake. A correct or uncertain prediction leaves the cause unresolved. A confirmed wrong prediction is a learner-reported hypothesis supported by one probe, not a verified causal account of all failures.

Confirmed hypotheses select targeted task variants where the ordinary topic transfer would not test that rule: saved-value semantics, spaces in strings, zero-based indexing and changed recursive base cases. Other probes select an existing relevant topic transfer. The exact stored task/check set is required for conquest. The replay preserves the prediction, its counterexample, the learner's attribution and the correct model. Mentor chat receives these distinctions as bounded data when the learner sends a message. No automatic AI request is added.

## VS Code handoff

Extension 0.2.4 adds **Diagnose & reassess on website**. It opens `/reassess?session=<connected session ID>`. The website uses an owner-authenticated recovery read (no automatic sign-in prompt), also checks the loaded plan, imports actual recorded test attempts once and links the transfer result to the original pattern.

A supported recovery requires C/Python, an exact supported concept label and an actual failing checkpoint with that exact concept label. A project title, framework keyword, aggregate test score, hint count or command exiting successfully is insufficient. Framework/project locks without an executable concept-specific transfer specification remain active, with the missing capability shown on the page. The website executes supported transfer tasks in its existing sandbox. It does not run arbitrary project workspaces remotely or certify full-project correctness.

Owner-verified imports use separate evidence scopes and require that owner at conquest time. Old unsigned imported conquests are quarantined as locked/unverified without deleting event history. A later sign-in does not promote them; verified re-import does not double skill points. The legacy bearer-only extension state endpoint remains unchanged and is not owner-authenticated.

A new website load can recover earlier extension attempts from the session's retained event history. Missing or truncated historical checkpoints are not reconstructed. Existing installed extensions must be updated to 0.2.4 to show the new button.

## Verification scope

- Local automated engine/store/history tests.
- All curated and diagnostic C/Python reference solutions execute against all their checks.
- Local isolated UI QA exercises confirmed prediction, targeted adaptation, failure feedback, reload, real GCC/Python execution, linked VS Code recovery and unsupported-project refusal.
- Authenticated production cloud write/RLS/read and cross-session hydration still require an isolated authenticated test identity. Serialization and source inspection are not that test.

Finite tests do not prove unaided work, active learning time, mental state, general mastery, genuine use of a construct or tamper-resistant certification. Elapsed time is wall-clock time. Do not present these patterns as independently verified beliefs or job credentials.

## Cloud restore safety

Cloud read errors, invalid saved JSON, and missing configuration fail closed. Only an error-free absent row is treated as no saved state. Restore failures keep cloud autosave paused and show a retry action without changing saved cloud data. Successful restore normalizes data locally but does not write a migration or upload local state merely because someone signed in. Google display names are used as a display fallback rather than silently editing the saved profile. A subsequent state change can save only after a successful restore/confirmed absence for the same current identity; stale restores and queued saves are ignored after identity changes.

Local automated checks exercise the actual client and CloudSync against a dummy HTTP service for permission, server, network, malformed-row, retry, no-row, existing-row normalization and explicit-edit/reload cases. This is not authenticated production persistence/RLS evidence. A real dedicated test identity and a supported test-only cleanup route are still required for a safe production fixture test.
